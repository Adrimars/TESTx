## 1. Apple Privacy Nutrition Label — data-type mapping

Apple's App Privacy Details defines these top-level data-type categories (developer.apple.com/app-store/app-privacy-details/): **Contact Info**, **Health & Fitness**, **Financial Info**, **Location**, **Sensitive Info**, **Contacts**, **User Content**, **Browsing History**, **Identifiers**, **Purchases**, **Usage Data**, **Diagnostics**, **Surroundings**, **Body**, **Other Data**. Each data type is then flagged as **linked to the user's identity** or not, and whether it's **used for tracking** (cross-app/cross-company ad targeting or sharing with a data broker) — both defined on the same page.

TESTx field mapping (see full table in the Action Checklist, §9d, for the submission-ready version):

- `email` → **Contact Info → Email Address**. Linked to identity (it *is* the identity).
- `googleId` → **Identifiers → User ID** (an account-linkage identifier from the third-party auth provider). Linked to identity.
- `passwordHash` → not declared. Apple's own examples exclude values a user never enters as personal data content and that exist solely to authenticate on-device against your own server; TermsFeed-style guides only address this by omission, not by rule text, so treat this as a low-confidence inference, not a citation — but it is universally treated as "not user data" across every filled-out label Apple has published guidance against (App Privacy Details page — no direct statement on password hashes; flagged as a reasonable industry-standard inference, not a directly cited rule).
- `age`, `gender`, `country`, `city` → **Contact Info → Physical Address** does *not* apply (no street address is collected); these fall to **Other Data** unless Apple's questionnaire in App Store Connect offers a closer bucket at data-entry time (Apple's public "data type" list on the App Privacy Details page does not include a dedicated "Demographics" bucket the way Google's form does — this is a real asymmetry between the two forms). None of age/gender/country/city are in Apple's **Sensitive Info** definition (racial/ethnic data, sexual orientation, pregnancy/childbirth, disability, religious/philosophical beliefs, trade union membership, political opinion, genetic info, biometric data — developer.apple.com/app-store/app-privacy-details/) — so do **not** over-declare these as Sensitive Info; they map to **Other Data**, linked to identity.
- `nativeLanguage`, `foreignLanguages`, `occupation`, `educationLevel`, `aiUseCases`, `aiExperience`, `aiFrequency` → **Other Data**, linked to identity (same reasoning — none matches a more specific category, none are Sensitive Info).
- `EvaluatorProfile.balance` (points) → **not Financial Info.** Apple's Financial Info category is explicitly Payment Info / Credit Info / Other Financial Info ("salary, income, assets, debts, or any other financial information" — developer.apple.com/app-store/app-privacy-details/); a points balance backed by no real currency and no purchase transaction doesn't fit any of the three. It also isn't **Purchases → Purchase History** (that's for IAP transaction records). The closest fit is **Usage Data → Other Usage Data** or **Other Data**, linked to identity, declared for **App Functionality** only. This mapping is an interpretation of Apple's published category definitions, not a directly-quoted rule for "points balances" specifically — flagged as inference.
- **Avatar selection (`avatarId`)** → since it's a small integer selecting a bundled preset image (not an uploaded photo), it is **not** User Content → Photos or Videos. It's an **Identifiers**-adjacent preference value, best declared as **Other Data**, linked to identity.
- **Google Sign-In itself**: Apple's page states developers must declare "all of the data you or your third-party partners collect" (developer.apple.com/app-store/app-privacy-details/). Google Sign-In returns the user's name/email as part of authenticating the primary account, and that returned data is inherently tied to a specific person to create the account — so it is linked-to-identity by Apple's own definition ("linked... unless you strip identifiers before collection and don't re-link them"). Apple's page does not contain a sentence specifically about "Google Sign-In" or "Sign in with Apple" — **this conclusion is drawn from the general linkage definition, not a named clause about third-party sign-in**, flagged accordingly.

**Data-use purposes** developers select per data type (developer.apple.com/app-store/app-privacy-details/): **App Functionality**, **Product Personalization**, **Analytics**, **Developer's Advertising or Marketing**, **Third-Party Advertising**, **Other Purposes**. For TESTx v1 (no ads, no cross-app tracking, no third-party analytics SDK mentioned in the plan), essentially every collected field should be declared **App Functionality** only (authenticate user, match tests to demographic filters, pay out rewards). If an analytics SDK (e.g. crash reporting) is added later, Diagnostics data gets an additional **Analytics** purpose at that time — don't pre-declare purposes you don't yet use.

## 2. Google Play Data Safety section — data-type mapping

Google's Data safety form groups declared data under: **Location**, **Personal info** (name, email address, user IDs, address, phone number, race/ethnicity, political/religious beliefs, sexual orientation, other demographic info), **Financial info** (purchase history, credit score, other financial info), **Health and fitness**, **Messages**, **Photos or videos**, **Audio files**, **Files and docs**, **Calendar**, **Contacts**, **App activity**, **Web browsing**, **App info and performance**, **Device or other IDs** (support.google.com/googleplay/android-developer/answer/10787469).

TESTx mapping:
- `email` → **Personal info → Email address**.
- `googleId` → **Device or other IDs** (or Personal info → User IDs, depending on how the console's sub-picker frames an OAuth subject identifier) — collected.
- `age`, `gender`, `country`, `city`, `nativeLanguage`/`foreignLanguages`, `occupation`, `educationLevel`, `aiUseCases`/`aiExperience`/`aiFrequency` → **Personal info → Other demographic info** (Google's category, unlike Apple's, explicitly names demographics — a real difference between the two forms worth building the mapping table around, §9d below).
- `balance` (points) → **not Financial info** on Google's form either — Financial info's subtypes (purchase history, credit score, other financial info) describe real monetary transactions; a non-monetary in-app points value with no purchase behind it doesn't fit. Best placed under **App activity → Other user-generated content** or left as an app-internal derived value not separately declared if Google's own guidance treats server-computed account state as out of scope — this is again an interpretation, not a directly quoted Google clause naming "points balances," flagged as such.
- **Avatar selection** → not Photos or videos (no photo is uploaded); it's a preference/setting, generally not separately declared unless the console's picker has a dedicated bucket for it.

**Does Google Drive import / Google Sign-In trigger "shares data with Google"?** This is the most important nuance in Q2 and the research confirms a clear distinction:
- **Google Sign-In / Google OAuth**: TESTx *sends* the user's Google credentials/token to Google to authenticate, and Google *returns* profile data (email, name) to TESTx. That returned data becomes data **TESTx collects**, declared under Personal info, exactly as with Apple. It is **not** "TESTx sharing user data outward to Google" in the policy sense — Google already has that data as the account holder. The support.google.com/googleplay/android-developer/answer/10787469 guidance on third-party SDKs is about **your app's own outward sharing to third parties for their own purposes** (ad networks, data brokers, cross-app profiling) — an OAuth login flow initiated by the user to authenticate is not that.
- **Admin importing media from Google Drive**: this is TESTx's *own* infrastructure pulling content Facebook/company already controls (Drive is admin-owned storage, not an evaluator's personal Drive) — it isn't user data flowing to a third party at all, so it doesn't trigger a "shares with Google" declaration either. If in the future evaluators connect their *own* Drive/Google accounts for something, that would need separate declaration.
- The genuinely relevant "sharing" question for TESTx's Data Safety form is: does TESTx send *evaluator* data (email, demographics) to any outward third party for the third party's own purposes? Per the current plan (no ad SDK, no analytics vendor named), the honest answer today is **no sharing**, only **collection** for the app's own functionality — which still must be fully declared, but the "Shared" toggle for those data types stays off. Reflected in the Data safety accuracy-audit context, §8 below.

**Encryption in transit**: Google's form asks whether "all user data collected by your app is encrypted in transit" (support.google.com/googleplay/android-developer/answer/10787469) — since Phase 9.1's bearer-token API calls should already run over HTTPS, answer yes, but this must be true for every endpoint including media delivery, not just auth.

**Data deletion**: the form asks whether the app "provides a way for users to request deletion of their data" (support.google.com/googleplay/android-developer/answer/10787469) — this ties directly into Q3 below and is currently a **hard gap** for TESTx.

## 3. Account deletion requirement — Apple 5.1.1(v) and Google Play equivalent

**Apple, current guideline text (developer.apple.com/app-store/review/guidelines/, §5.1.1(v)):**

> "If your app supports account creation, you must also offer account deletion within the app... Apps may not require users to enter personal information to function, except when directly relevant to the core functionality of the app or required by law."

Confirmed via Apple's own support article (linked directly from the guideline): **offering-account-deletion-in-your-app** — this requirement became mandatory for new submissions starting **June 30, 2022** (developer.apple.com/news/?id=12m75xbj, developer.apple.com/news/upcoming-requirements/?id=06302022b — both primary Apple News/Developer pages). Key specifics, confirmed on Apple's support page (secondary confirmation via search snippets, primary page itself not directly quotable line-by-line in this pass, flagged):
- **Deactivation/disabling alone does not satisfy the requirement** — it must be actual deletion, discoverable, not buried.
- **Support-mediated deletion is allowed only for apps in "highly-regulated industries"** requiring a phone call or email to complete deletion; TESTx (a general crowdsourcing/survey platform) is **not** such an industry, so it must offer a genuine **in-app, self-service** deletion path — a "contact us to delete your account" flow alone would not pass review.
- If a web page is needed to finish the flow, the app must **link directly** to that page (not just to a generic support/contact page).
- Apps that use Sign in with Apple must also revoke the user's Sign in with Apple token via Apple's REST API on deletion (only relevant if/when TESTx adds Sign in with Apple — see §6).

**Google Play, current policy (support.google.com/googleplay/android-developer/answer/13327111 — "Understanding Google Play's app account deletion requirements"):**
- If the app allows account creation, it must provide **both**: (a) an in-app path to request account + data deletion, and (b) a **web resource** (a URL, reachable outside the app) where the same request can be made — the web option matters for cases like a user who deleted the app itself.
- Deletion must remove the account **and** all associated user data that the Data Safety form declares as collected — not just deactivate it. "Temporary account deactivation, disabling, or 'freezing' the app account does not qualify as account deletion" (same source).
- Requests must be completed "within a reasonably quick period" (same source) — no fixed SLA is stated, unlike Apple's silence on timing too; both stores avoid a hard number but both explicitly reject indefinite/support-queue-only deletion.
- Legitimate retention (fraud prevention, legal/regulatory obligations — directly relevant to TESTx's KVKK-driven retention needs) is allowed but must be disclosed to the user (support.google.com/googleplay/android-developer/answer/10144311 — Google Play User Data policy: "you must clearly disclose your data retention and deletion policies").

**Verdict: this is a hard, confirmed blocker for both stores, not a nice-to-have.** TESTx currently has *only* sign-out (prd.md §15.9, plan.md §8.4) — no deletion path anywhere, web or mobile. Both Apple 5.1.1(v) and Google's account-deletion policy are phrased as unconditional requirements the moment an app supports account creation (which TESTx's email/password + Google registration flow clearly does), with no MVP/beta exception carved out in either primary source. **This will block submission to both stores as currently planned.** See the Action Checklist (§9a) for the concrete scoping recommendation.

## 4. Rewards/points economy — extra scrutiny?

**Apple** (developer.apple.com/app-store/review/guidelines/, §3.1 Payments and §5.3 Gambling/Contests):
- §3.1.1 governs unlocking paid functionality via Apple's own IAP; TESTx's points are **earned**, not purchased, so IAP rules for buying currency don't apply in the direction TESTx uses them (no user ever pays TESTx for points).
- "Any credits or in-game currencies purchased via in-app purchase may not expire" — not applicable, since TESTx points aren't sold.
- Loot-box odds-disclosure rules (§3.1.1 sub-clause) apply to randomized-item purchases — not applicable; TESTx's catalog is a fixed point-cost list, not a randomized draw.
- Sweepstakes/contests (§5.3.1–5.3.2) require the developer to be the sponsor and official rules to be shown in-app, with a disclaimer that Apple isn't involved — not applicable as long as redemption is deterministic (X points = specific coupon), not a random drawing. TESTx's design (fixed point cost per catalog item) is **not** sweepstakes-shaped.
- No Apple guideline was found treating "earn points for completing tasks, redeem for real-world value" apps as a distinct high-scrutiny category on its own. As corroborating (non-primary, observational) evidence, established apps of exactly this shape are live on the App Store today — SurveyMonkey Rewards, Google Opinion Rewards, Poll Pay, QuickThoughts — confirming this is a normal, accepted category, not itself a red flag.

**Google Play**: the closest documented policy is around **loyalty points tied to a monetary transaction** ("Loyalty points or rewards with benefits associated with a qualifying monetary transaction may only be awarded and redeemed on a fixed ratio basis... official rules for the program must be published within the app") and the separate, unrelated **incentivized-installs/reviews prohibition** (support.google.com/googleplay/android-developer/answer/9898684 — prohibits paying users specifically to leave ratings/reviews or install *other* apps; this does not describe TESTx's model, which rewards users for completing the app's own core task, not for reviewing or installing anything). TESTx's points aren't tied to a "qualifying monetary transaction" (no purchase occurs), so the fixed-ratio/official-rules clause likely doesn't formally apply either, though publishing simple, clear terms for how points are earned and (eventually) redeemed is good practice regardless.

**Does "no real redemption yet" reduce risk?** Yes, materially. Since prd.md §10.2a / §15.10 and plan.md Phase 14 explicitly gate the actual "spend" action behind a "Coming Soon" state with **zero balance mutation and no fulfillment**, TESTx v1 has **no real-world payout mechanism at all** — it's a scorekeeping/gamification feature with a browsable catalog, not a functioning rewards-redemption system. This is a meaningfully lower-scrutiny position than either "points redeemable for cash" (which would edge toward money-services/financial-app scrutiny, e.g. potentially Apple's real-money-services or Google's Financial Services policies neither of which were found to apply to TESTx's current design) or even "points redeemable for real coupons today" (which would need to state redemption terms, expiry, etc. up front). No red flags found for the "browsing-only, not yet spendable" design as long as store listings/descriptions don't overstate the catalog as functional (see §9e).

## 5. Age rating / 18+ gate

This is the one question where conflating two *different* mechanisms is the most likely mistake, so the distinction is worth stating plainly first:

- **In-app registration age gate** (plan.md Phase 9.3: self-declared age check blocking registration under 18) is a **product/legal control TESTx builds and owns**, aimed at sidestepping the unresolved TMK minor-consent question (kvkk-compliance-research.md §5). It has **no direct relationship** to either store's own classification system.
- **Store age-rating classification** (Apple's App Store Connect age-rating questionnaire; Google Play's IARC content-rating questionnaire) is a **content-based declaration** — both ask what's *in* the app (violence, sexual content, gambling, mature themes), not what your own registration policy is.

**Apple** (developer.apple.com/help/app-store-connect/reference/age-ratings-values-and-definitions/): current tiers are 4+, 9+, 13+, 16+, 18+ (Apple is migrating its rating system, with 12+/17+ being retired and a Jan 31, 2026 deadline for developers to complete the updated questionnaire in App Store Connect, after which failing to do so blocks new submissions — developer.apple.com/news/?id=ks775ehf-style Apple News item, confirmed via the same fetch). **18+ is triggered by actual content** — frequent alcohol/tobacco/drug references, frequent sexual content/nudity, frequent realistic violence, gambling or frequent simulated gambling. TESTx's actual content (evaluating admin-supplied photos/videos/audio for UX-style feedback) is **not** inherently any of those things — the content shown depends entirely on what tests admins create, but the *product itself* is not designed around mature content. Answering Apple's questionnaire honestly based on real app content, most likely lands TESTx at **4+ or 9+**, not 18+, **regardless of the in-app 18+ registration gate**. The fetched primary page does not describe any discoverability/featuring penalty tied specifically to a high age rating — only that Unrated apps can't publish at all — so a case for "declaring 18+ purely for consistency with the registration gate" would trade away discoverability for a rating that likely wouldn't even honestly reflect the app's content.

**Google Play** (support.google.com/googleplay/android-developer/answer/9867159 — Manage target audience and app content settings): declaring **"Ages 18 and over"** as the *target audience* is a **separate, optional declaration** from the IARC content questionnaire, and enables an optional **"Restrict Minor Access"** feature that actively blocks users Google's systems determine to be under 18 from finding/installing the app at all. This is a strong lever *if* TESTx wanted enforcement help from the platform itself, but it is not required merely because the app has an internal age gate — Google's own text frames it as a deliberate, opt-in choice, not a mandatory consequence of having adult registration logic.

**Recommendation:** keep the in-app 18+ registration gate exactly as planned (plan.md Phase 9.3) as the TMK/KVKK risk-mitigation mechanism, but **do not** force a hard 18+/adult content rating on either store's own questionnaire — answer both questionnaires honestly based on actual app content, which should land well below 18+ given the current concept (no mature/explicit content). Revisit only if TESTx later hosts genuinely mature evaluation content (explicit imagery, violence, etc.) as part of some future test category — at that point the content-based rating should follow the actual content, not the registration policy.

## 6. Google Sign-In and "Sign in with Apple" (Guideline 4.8)

**Current text (developer.apple.com/app-store/review/guidelines/, §4.8 Login Services):**

> "Apps that use a third-party or social login service (such as Facebook Login, Google Sign-In, Log in with X, Sign In with LinkedIn, Login with Amazon, or WeChat Login) to set up or authenticate the user's primary account with the app must also offer as an equivalent option another login service with the following features: the login service limits data collection to the user's name and email address; the login service allows users to keep their email address private as part of setting up their account; and the login service does not collect interactions with your app for advertising purposes without consent."

The guideline's carve-outs (own account system exclusively, education/enterprise SSO, government eID, or a client app requiring sign-in to a specific third-party service to access that service's content) **do not apply to TESTx** — TESTx offers Google Sign-In as one of two options.

**Does TESTx's existing email/password option already satisfy this?** No — read literally, §4.8 requires the *equivalent option* to be **"another login service"** with the three listed properties (name/email-only collection, private-relay email, no non-consensual ad-interaction tracking). A generic email/password form is not itself "a login service" in Apple's sense — it's the app's *own* account system. However, the guideline's first carve-out is exactly this case inverted: **"Your app exclusively uses your company's own account setup and sign-in systems"** exempts you *only if you use no third-party login at all*. Since TESTx **does** offer Google Sign-In (prd.md §15.9 makes it "equally prominent" on the entry screen), that exemption doesn't apply, and per the literal rule, offering email/password *alongside* Google Sign-In does **not** satisfy §4.8 — Sign in with Apple (or an equivalent qualifying third-party login) is specifically required **because** Google Sign-In is offered. This is a commonly-missed point precisely because it's counter-intuitive: having your own account system doesn't exempt you once *any* third-party social login is also offered.

**Implication for plan.md Phase 9**: Sign in with Apple needs to be added as a first-class option alongside Google Sign-In in Phase 9.3 (entry screen / auth flow), likely bundled with the same `expo-auth-session` mechanics already planned for Google, before iOS submission — not necessarily before Android submission, since 4.8 is an Apple-only guideline. See Action Checklist §9b for exact phase placement.

## 7. Media content review (admin-imported photo/video/audio)

Apple's user-generated-content moderation expectations (Guideline 1.2, developer.apple.com/app-store/review/guidelines/ — content filtering, a reporting mechanism, ability to block abusive users, and a published contact channel; secondary sources describe a "respond within 24 hours" operational norm, flagged as **not directly quoted from Apple's own guideline text** in this pass) are aimed at content that **other end users generate and other end users can see** — public/social UGC. TESTx's media is fundamentally different: it is **admin-curated content sourced from a controlled Google Drive**, shown only to evaluators as private rating material, with no evaluator-to-evaluator visibility and no evaluator ability to upload their own media into the pool. This is analogous to a market-research panel viewing pre-selected stimuli, not a UGC platform. **Low relevance is confirmed** — no reporting/blocking mechanism is expected here by either store's documented UGC policies, since there's no "user" content and no "generated" content in the sense the policies target. (No Google Play equivalent UGC-moderation clause was found that would apply differently here — the reasoning is symmetric.)

## 8. General submission checklist gaps

- **Privacy Policy URL (separate from the in-app KVKK text)**: Apple requires a **Privacy Policy URL field in App Store Connect** that must be publicly accessible without authentication, plus the same policy linked from within the app (Guideline 5.1.1 area — confirmed via Apple's own App Store Connect field requirement and cross-checked secondarily, since the exact clause text wasn't directly quotable from this pass's fetch; flagged as secondary-confirmed). Google Play requires the same idea under its User Data policy (support.google.com/googleplay/android-developer/answer/10144311): a privacy policy disclosing what's collected/used/shared, accessible both **in the app** and **in the Play Console listing**. **Neither of these is satisfied by the planned KVKK Aydınlatma Metni alone** — that's a KVKK Article-10 disclosure aimed at a specific Turkish legal requirement; the stores want a general privacy policy (which can *incorporate* the KVKK text, but needs to also cover the stores' required disclosure elements: what's collected, why, who it's shared with, retention/deletion). TESTx has **neither document drafted yet** (kvkk-compliance-research.md already flags the KVKK text itself as not drafted) — this is a second, related-but-distinct content gap.
- **Play Console target API level**: support.google.com/googleplay/android-developer/answer/11926878 and related Play Console Help pages — **new apps/updates must target Android 16 (API level 36) by August 31, 2026** (an extension to November 1, 2026 is requestable). Since today is 2026-08-24, this deadline is imminent — if `apps/mobile` is scaffolded on an Expo SDK whose default target API is older, this needs an explicit checkpoint before Android submission, not an assumption that "Expo handles it."
- **Apple Guideline 4.2 Minimum Functionality**: "Your app should include features, content, and UI that elevate it beyond a repackaged website... If your App doesn't provide some sort of lasting entertainment value or adequate utility, it may not be accepted" (developer.apple.com/app-store/review/guidelines/). TESTx's mobile app is a genuinely native, gesture-driven reinterpretation of the web product (§15.2–15.6) — not a wrapped webview — so this should not be a concern, but it's worth keeping in mind that a bare "webview + login" MVP would fail this guideline outright; the swipe/drag interaction work in Phases 9–11 is precisely what satisfies 4.2, not incidental polish.
- **Data Safety accuracy enforcement**: Google actively cross-references the declared Data Safety form against actual app/SDK behavior and can reject updates or take enforcement action on mismatches (support.google.com/googleplay/android-developer/answer/10787469 states the general principle that declarations must reflect actual behavior including third-party SDKs; the specific large-scale enforcement figures found in this research — e.g. app-removal/account-ban counts — come from secondary blog aggregation, not a primary Google transparency report, and are **flagged as secondary-source-only**). Practically: whoever fills out the Data Safety form must re-derive it from the actual `apps/mobile` network calls and SDKs at submission time, not from this document's field list alone, since SDKs (crash reporting, analytics, etc.) added later change the answer.
- **Age rating questionnaire deadline (Apple)**: separately from the 18+ discussion in §5, Apple's own migration to the new rating system has a **Jan 31, 2026 completion deadline for the questionnaire in App Store Connect**, after which incomplete questionnaires block submissions — since TESTx's mobile app hasn't shipped yet, this is moot for a first submission (the new questionnaire will simply be the only one available), but worth knowing if the admin/web side ever needs an App Store Connect record too.

## 9. TESTx Action Checklist (for prd.md / plan.md)

**(a) Account deletion — decisive: yes, must be added before store submission, both platforms.**
Neither store carves out an MVP exception; §3 above confirms both guidelines are unconditional the moment account creation exists, which TESTx's email/password + Google flow already does. Recommend:
- Add a new plan.md subsection — most naturally **Phase 9.4a "Account Deletion"**, right after the existing 9.4 Profile & Account Management (which currently only covers avatar/profile editing + logout) — covering: (1) an in-app "Delete Account" action reachable from the profile screen (not buried), with a confirmation step; (2) a backend `DELETE /users/me` (or similar) endpoint that deletes/anonymizes the `User` row, cascades `EvaluatorProfile` (already `onDelete: Cascade` in the schema), and disposes of `TestResponse` data per whatever retention TESTx settles on for quality-control/fraud-prevention purposes (both stores explicitly allow disclosed retention exceptions — see §3, §8); (3) a **web-reachable deletion request path** (even a simple hosted form or documented support email flow satisfies Google's "web resource" requirement, though a self-service in-app path should remain primary since TESTx is not a "highly-regulated industry" under Apple's narrow support-mediated exception). This should land **before** either store submission is attempted — it is the single most likely concrete rejection reason in this whole document.
- Decide now whether web (`apps/evaluator`) needs the same deletion capability — Apple/Google's rules are scoped to the *app under review*, so strictly only mobile needs it to pass store review, but shipping it API-side once naturally covers both surfaces, and KVKK's Article 11/7 deletion rights (kvkk-compliance-research.md §1, §6) apply regardless of platform — so building the backend capability once and exposing it from both clients is the more coherent move even though only mobile is store-gated.

**(b) Sign in with Apple — needs to be added, iOS-only requirement, lands in Phase 9.3.**
Per §6, offering Google Sign-In alongside email/password does not exempt TESTx from Guideline 4.8 on iOS. Add "Sign in with Apple" as a third auth option in the same entry-screen work as plan.md Phase 9.3 (same section that already builds the Google OAuth flow via `expo-auth-session`/`expo-web-browser`) — `expo-apple-authentication` is the natural Expo-ecosystem library for this. Not required for Android submission (4.8 is Apple-specific), so if Android ships first this can be sequenced as an iOS-specific addition to 9.3 rather than blocking the whole phase, but it must land before an iOS App Store submission specifically.

**(c) Age rating recommendation: keep the in-app 18+ registration gate; do not force a hard 18+ store content rating.**
Per §5, answer both stores' age-rating/content questionnaires honestly based on actual app content (likely 4+/9+ on Apple, a comparably low IARC tier on Google), and keep the TMK/KVKK-driven 18+ registration check as a purely product-side gate unrelated to those questionnaires. Do not enable Google's optional "Restrict Minor Access" feature unless TESTx later wants platform-level enforcement help beyond its own self-declared age check — it's a discoverability tradeoff not currently justified by the actual (non-mature) app content.
